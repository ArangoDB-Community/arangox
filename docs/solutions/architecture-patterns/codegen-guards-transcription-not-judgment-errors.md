# A code generator guards against transcription errors, not judgment errors

When a code generator's defects are all judgment failures — places where correct output required understanding the spec, not transcribing it — the generator is the wrong tool at exactly the points that matter. The fix is not a better generator. Freeze the generated corpus as owned, hand-maintained source; delete the generation machinery; and move the completeness guarantee into a verification gate, with the tested system itself as the oracle.

## Context

`lib/arangox/api/` holds 243 operation functions across 22 modules, one per ArangoDB API tag. The corpus was originally generated by `:oapi_generator` from a vendored, SHA-pinned copy of ArangoDB's OpenAPI document. The generator never stood alone: it accreted a 247-line preprocessor (`priv/openapi/preprocess.exs`, since deleted with the rest of the machinery), an 84-line custom renderer, a 288-line README explaining the pipeline, a waiver list in the old gate, a never-hand-edit rule, dialyzer ignore entries for the renderer, a `.gitattributes` linguist marking, and a CI (continuous integration) regenerate-and-diff job. Commit `62a5b47` on `feat/v0-8-modernization` (unpushed at time of writing) shows the full inventory at deletion: roughly 35,000 lines removed, most of it the 34,656-line vendored document.

A security review and two peer review rounds found real defects in the generated surface. Every one was a judgment failure:

1. **Fragments rendered into request URLs.** The document distinguishes two operations sharing a path and method by appending a URL fragment to the path key (`/_api/document/{collection}#get`). The fragment is documentation — the server ignores it — but the generator emitted it into the request URL, breaking the 15 operations whose path keys carry one.
2. **A required flag that is a safety boundary.** The generator emits every query parameter as optional. `getDocuments` shares `PUT /_api/document/{collection}` with `replaceDocuments`; only `onlyget=true` on the wire makes the server read instead of replace. Generated as optional, a call asking to read documents would silently replace them. The operation had to be withheld from generation entirely.
3. **Non-JSON bodies routed through the JSON codec.** Operations declaring `text/plain` or octet-stream request bodies had them encoded as JSON anyway.
4. **Typespecs contradicting reality.** Generated specs described returns the adapter never produces.

The generator made zero transcription errors. Its entire defect class was judgment — and the machinery around it existed to defend a guarantee ("the surface matches the spec") that the generator never provided. The gate provided it.

Three details from the generation era sharpen the picture (session history):

- **The first fragment fix was itself wrong, in a judgment-shaped way.** Stripping fragments from the document's path keys at preprocess time would have collided every fragment key with an existing canonical path+method; a naive `Map.put` would have silently overwritten the canonical operation, converting a wrong-URL bug into 15 operations *missing* from the surface. The working fix stripped the fragment only at URL-render time, leaving operation identities untouched.
- **The `getDocuments` trap was exposed by the fragment fix.** Before it, the corrupted URL 404'd on every call — broken but harmless. The moment the URL became well-formed, the same generated function became a live path to the destructive bulk replace with `onlyget` omitted. Fixing one generator defect armed another.
- **The typespec mismatch was invisible to dialyzer** because the client module is resolved at runtime (`opts[:client] || @default_client`), making the call target opaque to static analysis. The review, not the tooling, caught it.

## Guidance

The steps, in the order they landed (`c912278` through `d35637c`, pending on `feat/v0-8-modernization`; every commit SHA in this doc is branch-local and may be rewritten if the branch is rebased or squashed before merge):

**1. Hand-write the judgment cases first.** `getDocuments` was reinstated by hand (`c912278`) with the safety decision in the operation's own body, structured so no caller input can defeat it:

```elixir
# lib/arangox/api/documents.ex:628-631
query =
  opts
  |> Keyword.take([:ignoreRevs])
  |> Keyword.put(:onlyget, true)
```

`Keyword.put` after `Keyword.take`: a caller-supplied `onlyget: false` is dropped by the take and overwritten by the put, so the destructive form of the request cannot be produced through this function. The docstring warns that an `onlyget` value in `opts` is ignored rather than forwarded (`lib/arangox/api/documents.ex:599-604`).

**2. Verify the live oracle equals the vendored one, then build the gate against the live oracle — before deleting anything.** The vendored document and the document the compose 3.12 server serves were diffed first: identical paths, operations, parameter sets, and request media; the only differences were a float-precision artifact in one schema default and the format of `info.version`. That last difference is why the gate's version check reads `/_api/version` and never `info.version` (`test/arangox/api/conformance_test.exs:419-432`). The gate (`f491714`) fetches `GET /_db/_system/_admin/aardvark/api/swagger.json` from the tested server and refuses to compare anything until `Errno.tag/0` — the repo's single version pin — equals the live server's answer, so a mis-pinned stack fails on the actual problem instead of drowning it in operation noise.

**3. Make the gate deep enough to carry the guarantee alone.** The conformance gate proves, per run:

- a multiset method/path bijection between document and surface, with no waiver list — an absence in either direction fails, and a duplicated operation matched once still fails (`test/arangox/api/conformance_test.exs:445-464`, `734-744`);
- within each `{method, template}` address group, matching multisets of `{query key set, request media}` (`466-499`) — grouping is needed because after fragment stripping nine addresses legitimately carry more than one operation, 24 in all (`conformance_test.exs:17-26`);
- pinned cardinality — 164 paths, 243 document operations, 243 extracted call sites (`59-60`, `746-758`) — so an extraction or parse regression cannot shrink a side to the empty set and pass vacuously;
- a checked-in required-query-parameter watch, 42 `{operationId, name}` pairs (`106-149`, test at `501-521`), so a parameter changing required-ness at a future pin forces a human decision;
- a checked-in `operationId → module → function` identity mapping, 243 triples (`160-409`, test at `523-548`);
- an `args:`/URL cross-check (`618-633`), because the adapter's path-parameter refusal (`check_path_args` in `lib/arangox/api/client.ex:104-118`) sees only values listed under `args:` — a parameter interpolated into the URL but missing from `args:` would silently skip validation, and no address comparison can see that.

Equally important: the extractors fail loudly. A query construction the extractor does not recognize is `{:unrecognized, description}` and fails the gate naming the site (`933-940`, `974`); unrecognized request-media and `args:` entries `flunk` (`1000`, `1013`). The recognized query shapes are deliberately few — absent, literal `[]`, a `Keyword.take` of literals, and exactly one injection: the `onlyget` pipe (`963-972`). Anything else must be added deliberately, not skipped silently.

**4. Split what needs no server into a unit gate.** `test/arangox/api/surface_test.exs` (`b6ac172`) runs in plain `mix test`, no Docker: an adapter-seam denylist proving no operation file references a transport (`28-49`), no `#` in any emitted URL (`64-69`), no un-interpolated `{param}` (`57-62`), and the pinned 243 call-site count (`76-88`). Both tiers read the surface through one shared extraction module, `test/support/api_surface.ex`, so they cannot disagree about what counts as an operation file or a call site (`f887f76`).

**5. Delete the machinery in a commit that changes no production code.** `62a5b47` removes the dependency, config, preprocessor, renderer, vendored document, CI job, and ignore entries — and its message records that the `lib/` diff against its parent is empty, which is independently checkable.

**6. Document the ownership change where the next maintainer will look.** `4816651`: the "The API surface" section of `AGENTS.md` (owned source, the two gates, the fidelity gaps with instructions for re-deriving their counts from the live document), and the user-facing disclosure in `README.md:324-328` ("spec-derived but owned: hand-maintained source, verified ... against the OpenAPI document the tested server itself serves").

**7. Prove the gate can fail.** Mutation probes recorded in `f491714`'s message: a renamed take key, a changed media type, an altered URL segment (reported in both directions), a wrong version pin (fails in `setup_all`), and an unrecognized query shape (fails naming the site) — with the mutated file restored byte-identical afterward, shasum-checked.

## Why This Matters

**Judgment versus transcription.** A generator is a transcription machine. When every observed defect requires understanding — that a fragment is not an address, that one "required" flag separates a read from a bulk replace, that a declared media type selects a codec — the generator fails precisely where failure is expensive and succeeds only where it was never at risk. That distribution of defects is the signal to stop generating.

**Regeneration re-imports unknown-unknowns.** A corpus that has survived a security review and two peer reviews is a known quantity. Regenerating replaces it wholesale with fresh output that must be re-audited for the same class of silent failures, every time the pin moves. The waiver list only grows. Freezing converts a recurring audit into a one-time one.

**Checking is much simpler than producing.** The production side was a preprocessor, a renderer, generator config, a CI job, and a 34,656-line vendored blob. The checking side is two test files and a 149-line shared extractor. The completeness guarantee always lived in the gate; retiring the generator removed the machinery, not the guarantee.

**One pin instead of two, and a stronger claim.** The vendored document and the vendored errno table each pinned a server version, and they could drift apart. Now `Errno.tag/0` is the single pin, asserted against the live `/_api/version` before any comparison (`test/arangox/api/conformance_test.exs:425`). "Verified against the document the tested server itself serves" is also a more honest claim than "generated from a blob we downloaded once" — the oracle and the system under test cannot disagree about which version they are.

## When to Apply

All of these held here, and all should hold before applying the pattern:

- **The generator's defects are judgment-shaped.** If the defects are transcription errors — typos, encoding bugs, mis-mapped fields — fix the generator; that is what generators are good at.
- **The corpus has survived real review.** The guarantee transfers from authorship to verification only if verification actually happened. Freezing an unreviewed corpus bakes in unaudited output.
- **A strong gate exists or can be built** — one that detects the drift the generator used to absorb (operations added or removed, parameter sets changed, media changed) and reports it as a concrete worklist. The gate replaces the generator's one legitimate job.
- **The tested system can serve as the oracle.** Here the compose stack already ran in CI, serves its own OpenAPI description, and that description was verified equivalent to the vendored one before the switch.

Do not apply when:

- **The upstream spec churns fast.** Hand-applying drift each release can cost more than re-auditing regeneration. (ArangoDB moves one minor at a time; the update procedure in `AGENTS.md` under "Updating to a new server tag" is: bump the pin, run the gate, hand-apply the reported drift.)
- **There is no verification surface.** Freezing without a gate is abandoning the corpus, not owning it.
- **The corpus was never reviewed**, or the rejected alternative actually fits: adapter-level special cases were rejected here because safety belongs in the operation's own code and the adapter stays operation-agnostic, and a from-scratch rewrite was rejected because the verification, not the authorship, carried the guarantee.

## Examples

**getDocuments — the archetype of judgment in code.** The server distinguishes this read from `replaceDocuments` by nothing but `onlyget=true` — same path, same method. The judgment lives in the operation body (the take-then-put above), not in the adapter, and the gate then guards the guard three ways: the query extractor's one recognized injection is exactly this pipe (`test/arangox/api/conformance_test.exs:963-972`), the required-parameter watch pins `{"getDocuments", "onlyget"}` (`121`), and the profile comparison notes that the PUT document path is the only group whose members differ in query sets — `onlyget` is what tells the siblings apart (`760-763`).

**The fragment convention — the same defect watched at two tiers.** The gate strips fragments before comparing addresses (`853`) and documents the convention in its moduledoc (`17-26`); the unit tier independently refuses any `#` in an emitted URL (`test/arangox/api/surface_test.exs:64-69`), Docker-free. The defect that originally broke 15 operations now cannot re-enter through either an edit to the surface or drift in the document.

**The identity mapping — catching what address profiles cannot.** Sibling operations at one address can share query and media profiles (the eight POST variants on the index path do), so a renamed function — or one deleted with its sibling duplicated — passes the bijection and profile checks while callers lose a function. The checked-in 243-triple mapping (`test/arangox/api/conformance_test.exs:160-409`, test at `523-548`) fails on exactly that, and doubles as proof of the naming rule: at the current pin, every function name is exactly `Macro.underscore(operationId)`.

**One assertion over every operation, not one test per bug.** When the generation-era review asked whether the 15 corrupt URLs should get 15 test cases, the answer was one assertion over every emitted URL — it covers all 243 operations and catches the next fragment that arrives, not just the ones already seen (session history). The owned-surface gates keep that shape: every check above quantifies over the whole surface.
