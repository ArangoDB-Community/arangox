# A code generator guards against transcription errors, not judgment errors

When a code generator's defects are all judgment failures — places where correct output required understanding the spec, not transcribing it — the generator is the wrong tool at exactly the points that matter. The fix is not a better generator. Freeze the generated corpus as owned, hand-maintained source; delete the generation machinery; and move the completeness guarantee into a verification gate, with the tested system itself as the oracle.

## Context

`lib/arangox/api/` holds 230 operation functions across 22 modules, one per ArangoDB API tag. The corpus was originally generated by `:oapi_generator` from a vendored, SHA-pinned copy of ArangoDB's OpenAPI document. The generator never stood alone: it accreted a preprocessor, a custom renderer, a README explaining the pipeline, a waiver list in the old gate, a never-hand-edit rule, dialyzer ignore entries for the renderer, a `.gitattributes` linguist marking, and a CI (continuous integration) regenerate-and-diff job. Deleting the machinery removed roughly 35,000 lines, most of it the 34,656-line vendored document.

A security review and two peer review rounds found real defects in the generated surface. Every one was a judgment failure:

1. **Fragments rendered into request URLs.** The document distinguishes two operations sharing a path and method by appending a URL fragment to the path key (`/_api/document/{collection}#get`). The fragment is documentation — the server ignores it — but the generator emitted it into the request URL, breaking the 15 operations whose path keys carry one.
2. **A required flag that is a safety boundary.** The generator emits every query parameter as optional. `getDocuments` shares `PUT /_api/document/{collection}` with `replaceDocuments`; only `onlyget=true` on the wire makes the server read instead of replace. Generated as optional, a call asking to read documents would silently replace them. The operation had to be withheld from generation entirely.
3. **Non-JSON bodies routed through the JSON codec.** Operations declaring `text/plain` or octet-stream request bodies had them encoded as JSON anyway.
4. **Typespecs contradicting reality.** Generated specs described returns the adapter never produces.

The generator made zero transcription errors. Its entire defect class was judgment — and the machinery around it existed to defend a guarantee ("the surface matches the spec") that the generator never provided. The gate provided it.

Three details from the generation era sharpen the picture:

- **The first fragment fix was itself wrong, in a judgment-shaped way.** Stripping fragments from the document's path keys at preprocess time would have collided every fragment key with an existing canonical path and method; a naive `Map.put` would have silently overwritten the canonical operation, converting a wrong-URL bug into 15 operations *missing* from the surface. The working fix stripped the fragment only at URL-render time, leaving operation identities untouched.
- **The `getDocuments` trap was exposed by the fragment fix.** Before it, the corrupted URL 404'd on every call — broken but harmless. The moment the URL became well-formed, the same generated function became a live path to the destructive bulk replace with `onlyget` omitted. Fixing one generator defect armed another.
- **The typespec mismatch was invisible to dialyzer** because the client module is resolved at runtime (`opts[:client] || @default_client`), making the call target opaque to static analysis. The review, not the tooling, caught it.

## Guidance

The steps, in the order they landed. This doc cites file and line rather than revisions: the branch has been squashed once already, and every commit identifier an earlier version of this doc carried is now unresolvable.

**1. Hand-write the judgment cases first.** `getDocuments` was reinstated by hand, with the safety decision in the operation's own request spec rather than in the adapter:

```elixir
# lib/arangox/api/documents.ex:370-380
def get_many(conn, collection, body, opts \\ []) do
  Client.request(conn,
    method: :put,
    segments: ["_api", "document", collection],
    body: body,
    forced: [{"onlyget", "true"}],
    query: [ignore_revs: "ignoreRevs"],
    opts: opts
  )
end
```

A forced parameter is the operation's own and is always sent; only parameters named under `query:` can be set by a caller. Because `onlyget` appears in `forced:` and not in `query:`, a caller-supplied `onlyget: false` is never read, so the destructive form of the request cannot be produced through this function. The docstring carries the server's warning that this address replaces documents without the flag (`lib/arangox/api/documents.ex:344-350`).

**2. Verify the live oracle equals the vendored one, then build the gate against the live oracle — before deleting anything.** The vendored document and the document the compose 3.12 server serves were diffed first: identical paths, operations, parameter sets, and request media; the only differences were a float-precision artifact in one schema default and the format of `info.version`. That last difference is why the gate's version check reads `/_api/version` and never `info.version` (`test/arangox/api/conformance_test.exs:62-78`). The gate fetches `GET /_db/_system/_admin/aardvark/api/swagger.json` from the tested server and refuses to compare anything until `Errno.tag/0` — the repo's single version pin — equals the live server's answer (`:71`), so a mis-pinned stack fails on the actual problem instead of drowning it in operation noise.

**3. Make the gate deep enough to carry the guarantee the generator used to claim.** The conformance gate proves, per run:

- pinned cardinality — 243 documented operations at 228 distinct addresses, against 230 surface operations (`test/arangox/api/conformance_test.exs:54-56`, test at `91-105`) — so an extraction or parse regression cannot shrink a side to the empty set and pass vacuously;
- every documented address is reachable from the surface (`109-121`) and every address the surface calls is documented (`123-135`);
- every query key the surface sends, forced or offered, is documented at its address (`139-154`);
- every required query parameter is either forced or offered, compared per address rather than per operation (`159-185`);
- a declared non-JSON request media matches what the surface sends (`189-206`).

Addresses are compared as **sets**, not one-to-one. The description documents one endpoint several times when it takes more than one body or answers more than one shape — eight documented ways to create an index, all `POST /_api/index` — while the surface carries one operation per address plus two deliberate extras (`conformance_test.exs:16-25`, `46-53`). Parameters are compared by position, because the document writes `{collection-name}` where the surface's argument is `collection_name` (`250-260`).

Be precise about what this does and does not carry. Every dimension above is a shape the description states, so the gate proves the surface addresses the right endpoints under the right parameter names. It does not prove a call works. Two limits are worth naming:

- **Values are outside its reach.** A parameter whose value has internal structure the description never mentions is invisible here. That is not hypothetical: encoding a composite index identifier as though it were one opaque segment broke every index read and delete while both gates stayed green — see [Encoding every path segment alike breaks index ids, which are themselves paths](../logic-errors/percent-encoding-every-path-segment-breaks-composite-index-ids.md).
- **Names are outside its reach.** The gate compares addresses; the unit tier pins the operation count. Neither pins function names, so renaming an operation passes both. An earlier gate carried a checked-in `operationId → module → function` mapping; the surface rewrite removed it, and nothing replaced it.

**4. Split what needs no server into a unit gate.** `test/arangox/api/surface_test.exs` runs in plain `mix test`, no Docker: an adapter-seam denylist proving no operation file references a transport (`33-55`), every path segment a literal or a bare argument with no literal carrying `{`, `}`, `#` or `?` (`62-73`), a bang twin of the same arity for every operation (`77-92`) that delegates rather than issuing its own request (`94-100`), no parameter both forced and offered (`107-115`), and the pinned operation count (`119-126`). Both tiers read the surface through one shared extraction module, `test/support/api_surface.ex`, so they cannot disagree about what counts as an operation or a call site. That module raises on any segment shape it does not recognize, so reaching the segment assertion at all is most of its proof.

**5. Delete the machinery in a commit that changes no production code.** The deletion commit removed the dependency, config, preprocessor, renderer, vendored document, CI job, and ignore entries, and its message recorded that the `lib/` diff against its parent was empty — a claim a reviewer can check independently.

**6. Document the ownership change where the next maintainer will look.** The "The API surface" section of `AGENTS.md` carries the owned-source rule, the two gates, and the fidelity gaps with instructions for re-deriving their counts from the live document. The user-facing disclosure is in `README.md:358` — "spec-derived but owned: hand-maintained source, checked by the" gates rather than regenerated.

**7. Prove the gate can fail.** Mutation probes were run and recorded when the gate landed: a renamed take key, a changed media type, an altered URL segment (reported in both directions), a wrong version pin (fails in `setup_all`), and an unrecognized query shape — with the mutated file restored byte-identical afterward, shasum-checked. A gate nobody has watched fail is a gate nobody knows the reach of.

## Why This Matters

**Judgment versus transcription.** A generator is a transcription machine. When every observed defect requires understanding — that a fragment is not an address, that one "required" flag separates a read from a bulk replace, that a declared media type selects a codec — the generator fails precisely where failure is expensive and succeeds only where it was never at risk. That distribution of defects is the signal to stop generating.

Freezing does not eliminate the transcription-error class, though. It relocates it. Encoding rules, separator handling and argument interpolation now live in a hand-written adapter, where no generator produces them and no description-comparison gate inspects them.

**Regeneration re-imports unknown-unknowns.** A corpus that has survived a security review and two peer reviews is a known quantity. Regenerating replaces it wholesale with fresh output that must be re-audited for the same class of silent failures, every time the pin moves. The waiver list only grows. Freezing converts a recurring audit into a one-time one.

**Checking is much simpler than producing.** The production side was a preprocessor, a renderer, generator config, a CI job, and a 34,656-line vendored blob. The checking side is two test files and one shared extractor. The guarantee that always lived in the gate is a completeness guarantee — every documented address reachable, every called address documented — and retiring the generator removed the machinery, not that guarantee. Completeness is not correctness: a surface can be complete by this definition and still non-functional.

**One pin instead of two, and a stronger claim.** The vendored document and the vendored errno table each pinned a server version, and they could drift apart. Now `Errno.tag/0` is the single pin, asserted against the live `/_api/version` before any comparison (`test/arangox/api/conformance_test.exs:71`). "Verified against the document the tested server itself serves" is also a more honest claim than "generated from a blob we downloaded once" — the oracle and the system under test cannot disagree about which version they are.

## When to Apply

All of these held here, and all should hold before applying the pattern:

- **The generator's defects are judgment-shaped.** If the defects are transcription errors — typos, encoding bugs, mis-mapped fields — fix the generator; that is what generators are good at. Note where those defects will live afterward: freezing moves them into the hand-written code that replaces the generator.
- **The corpus has survived real review.** The guarantee transfers from authorship to verification only if verification actually happened. Freezing an unreviewed corpus bakes in unaudited output.
- **A strong gate exists or can be built** — one that detects the drift the generator used to absorb (operations added or removed, parameter sets changed, media changed) and reports it as a concrete worklist. The gate replaces the generator's one legitimate job. Ask the complementary question before freezing: what does the spec leave unstated? Value formats, encoding rules, and structure inside a parameter are not in the document, so no gate built on the document will check them — arrange to exercise those against a live system instead.
- **The tested system can serve as the oracle.** Here the compose stack already ran in CI, serves its own OpenAPI description, and that description was verified equivalent to the vendored one before the switch.

Do not apply when:

- **The upstream spec churns fast.** Hand-applying drift each release can cost more than re-auditing regeneration. (ArangoDB moves one minor at a time; the update procedure in `AGENTS.md` under "Updating to a new server tag" is: bump the pin, run the gate, hand-apply the reported drift.)
- **There is no verification surface.** Freezing without a gate is abandoning the corpus, not owning it.
- **The corpus was never reviewed**, or the rejected alternative actually fits: adapter-level special cases were rejected here because safety belongs in the operation's own code and the adapter stays operation-agnostic, and a from-scratch rewrite was rejected because the verification, not the authorship, carried the guarantee.

## Examples

**getDocuments — the archetype of judgment in code.** The server distinguishes this read from `replaceDocuments` by nothing but `onlyget=true` — same path, same method. The judgment lives in the operation's request spec, not in the adapter, and the gates then guard the guard from both tiers. The unit tier refuses any parameter that is both forced and offered (`test/arangox/api/surface_test.exs:107-115`), which is what keeps a caller from handing back the choice. The integration tier checks required-parameter reachability per address rather than per operation (`test/arangox/api/conformance_test.exs:159-185`), because `get_many` must force `onlyget` and `replace_many` must not — sending it is exactly what would turn the replace into a read.

**The fragment convention — the same defect watched at two tiers.** The gate strips fragments before comparing addresses (`conformance_test.exs:240-248`) and documents the convention in its moduledoc (`16-25`); the unit tier independently refuses a literal path segment carrying `{`, `}`, `#` or `?` (`surface_test.exs:62-73`), Docker-free. The defect that originally broke 15 operations cannot re-enter through either an edit to the surface or drift in the document.

**One assertion over every operation, not one test per bug.** When the generation-era review asked whether the 15 corrupt URLs should get 15 test cases, the answer was one assertion over every emitted URL — it covers every operation and catches the next fragment that arrives, not just the ones already seen. The owned-surface gates keep that shape: every check above quantifies over the whole surface.
